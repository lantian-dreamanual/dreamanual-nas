## 一句话结论

**播放链路和改标签都成立，可以照这个做。** 取曲库、取流播放（两条路可选）、改标签并落盘，三件都在真实 NAS 上验通。改标签那一次只动了一份临时副本，原始文件全程只被读、被复制。

**四个模块都验通了**（2026-10-11 深夜收口）：听歌（曲库取歌带流派 + 取流 + 写 ID3）、文件管理（列目录 / 取封面 / 取缩略图）、关机与计划开关机（接口与权限齐，**真关机未试**）、相册（共享空间按目录浏览 + 缩略图）。~~相册做不了「按相册分组」~~（**10-18 更正**：`Browse.Album` 一套接口 + `team_space` 参数，两个空间各一库，见第七节第 4 条）。

**外网走 QuickConnect，不要走 Tailscale** —— 同一个接口请求，QuickConnect 0.15 秒、Tailscale 2.5 秒；取流吞吐 1.18 MB/s 对 16 KB/s。**远程播放实测与本地没有可感差别**（第五节）。

**管理类接口已全部收口**（2026-10-12 凌晨）：文件管理的写操作（建目录 / 上传 / 改名 / 复制移动 / 删除）写法全部定死，可写性判据也定了（`perm.acl.write`）。另外查清了 `FileStation.Search` 的脾气 —— **它会随机返回假空，`total` 还是过程值**，界面上要用它必须带重试、并且轮询到 `finished=true`（见第七节第 1 条末）。

**两处早前的结论被推翻**：上传 `overwrite=false` **不会**覆盖同名文件（回「成功」但内容不变），`Rename` 撞名也**不会**覆盖（回 `1200` + `errors[414]`）。

**歌词面板与曲库检索都恢复立项**（2026-10-12）：歌词接口读文件内嵌，但全库只有约 0.3% 的曲目带，主力走在线搜索（服务端已装插件）；曲库搜索、随机播放、评分读取都有原生接口，评分筛选与歌单取歌的绕法见第八、九节。**系统状态页的字段与单位坑见第十节。**

**封面取图改走目录**（2026-10-13）：同名但不同源的专辑只要都缺 `album_artist` 标签，DSM 会并成一张专辑实体、只给一张图（实测「0」并了 Low Roar / Superfly / 林忆莲 三家），按专辑名取图必然串台 —— 首选曲库目录里的图片文件，`cover.cgi` 只当兜底（第二节）。

**原文件下载可行**（2026-10-13）：曲库那条 `path` 直喂 `FileStation.Download` v2 `mode=open` 就能拿回原始 MP3。**失败有两种形状** —— 会话问题回 HTTP 200 + JSON `code=119`、路径问题回 HTTP 404 + HTML，两条判据都得写（第十一节）。

## 一、连接与鉴权

登录：

```
POST /webapi/auth.cgi
api=SYNO.API.Auth&version=6&method=login&session=AudioStation
   &account=…&passwd=…&format=sid&enable_syno_token=yes
```

返回 `data.sid`（会话）与 `data.synotoken`。

### 🔴 两套鉴权入口，规矩不一样

| 目标 | 表单 `_sid` | Cookie `id=<sid>` | 请求头 `X-SYNO-TOKEN` |
|---|---|---|---|
| `/webapi/…`（公开接口） | 要 | 不用 | 登录申请了 token 就必须带 |
| `/webman/3rdparty/…`（内部 CGI） | 要 | **要** | **要** |

- 内部 CGI 缺 Cookie → `{"errno":{"key":"error_noprivilege","section":"login"}}`；缺 token → `common/error_system`；**把 token 放表单里也报 `error_system`（只认请求头）**。
- `/webapi/` 只认表单 `_sid`，给 Cookie 反而回 `code=105`。
- **登录带了 `enable_syno_token=yes`，之后所有 `/webapi/` 请求都得带 `X-SYNO-TOKEN`** —— 不带就 `code=105`、返回 0 条数据（实测同一个歌单请求，不带 0 首、带了 50 首）。

🔴 **`query.cgi` 返回的 `path` 是相对路径**（`entry.cgi`，不是 `/webapi/entry.cgi`）。拼接前必须补前缀，否则 `URL(string:)` 得到非法 URL，强解包直接崩。

### 🔴 要登两个会话，sid 与 synotoken 必须成对

`session` 参数决定这个会话被授予哪一套应用权限（2026-10-11 实测）：

| 接口类 | 用哪个会话 |
|---|---|
| 曲库（`AudioStation/*.cgi`） | **`session=AudioStation`** |
| 文件 / 相册 / 系统类 | **`session=FileStation`** |

- **拿 A 会话的 `sid` 配 B 会话的 `synotoken` → 一律回 `code=105`（权限不足）。** 这个错误形态看起来像权限问题，实际是配错了对 —— 有一轮曲库 13 条全 105 就是这么来的。（码随接口变：同一种配错，`FileStation.Download` 回的是 **119** 不是 105 —— 见第十一节第 5 条。）
- `session=SynologyPhotos` 也能登（相册缩略图不需要它，FileStation 就够）。
- 登录端点 `/webapi/entry.cgi` 与 `/webapi/auth.cgi` **两个都能用**（同一轮里 auth.cgi 偶尔回 119、重跑又通，机制未查明）。稳妥做法：两种都试，哪条打 `SYNO.Core.System.info` 心跳通用哪条，失败的那条立刻登出，别占会话名额。
- 🔴 **别用「全局变量当默认凭证」**：忘了赋值就静默变空串，所有请求都少一个 `X-SYNO-TOKEN` 头，表现为一堆 105，很难看出是脚本自己的错。

### `SYNO.API.Auth` 的业务码 —— 登录失败先怀疑凭据，别怀疑端点

2026-10-12 复测（中继端点下 `auth.cgi` 与 `entry.cgi` 各打一次，同一账号同一密码）：**两条都回 `success: true`**。所以「登录不通」这件事，端点、参数形状、`enable_syno_token` 都已被排除，剩下的只能是账号或密码本身。

`SYNO.API.Auth` 的 `error.code` 语义（**换 API 就不成立** —— 同一个 `400` 在 FileStation 是「路径不合法」）：

| code | 含义 |
|---|---|
| 400 | 账号不存在或密码不对 |
| 401 | 账号已停用 |
| 402 | 权限不足 |
| 403 / 406 | 账号开了两步验证，要验证码 |
| 404 | 验证码不对 |
| 407 | 来源 IP 被自动封锁 |
| 408 / 409 | 密码已过期，需先改 |

界面做法：**只翻 `SYNO.API.Auth` 这一组**，其余保留原始 `api.method（code N）`（码本身是查文档的钥匙，翻错方向比不翻更糟）。另：账号密码类的错**换端点重试没有意义**，重打只会把失败次数翻倍，而 DSM 的自动封锁正是照失败次数记的。

### 客户端请求的 UA（2026-10-16 实测）

Python `urllib` 用默认 UA（空）打 QuickConnect `Serv.php`，同一个请求体会回 **`errno 4 / Alias not found`** —— 看起来像 QC ID 不存在，其实是 UA 被拦；同参数换 curl 就 `errno 0`。

- **只影响脚本探针**：NAS 助手走 URLSession、UA 是系统默认，`request_tunnel` 与全部 Audio Station 接口实测都通，不需要为它改动。
- 写探针一律用 curl，或给请求显式带一个 UA。**别拿 `errno 4` 当「QC ID 拼错」的判据** —— 先确认 UA。

## 二、曲库与取流

取歌单：

```
POST /webapi/AudioStation/song.cgi
api=SYNO.AudioStation.Song&version=3&method=list
   &limit=50&offset=0&additional=song_tag,song_audio&_sid=<sid>
＋ 请求头 X-SYNO-TOKEN
```

返回在 `data.songs`。实读总数 **12331 首**。

🔴 **`additional` 必须给逗号串，不能给 JSON 数组。** 给 `["song_tag","song_audio"]` 时 DSM **一条标签都不带回来**（返回的条目只剩 `id / path / title / type`），给 `song_tag,song_audio` 才有。**跟 FileStation 的 `additional`（数组、逗号串都认）不一样，更跟 `folder_path`（只认纯字符串、给数组必 502）正好相反 —— 每个接口要单独试。**

条目字段（实测）：

| 位置 | 字段 |
|---|---|
| 顶层 | `id`（`<song id>`）/ `path`（`/music/<歌手>/<年.专辑>/<轨道>.<标题>.mp3`）/ `title` / `type` |
| `additional.song_tag` | `album` / `album_artist` / `artist` / `comment` / `composer` / `disc` / `genre` / `track` / `year` |
| `additional.song_audio` | `bitrate` / `channel` / `codec` / `container` / `duration`（**秒**）/ `filesize` / `frequency` |

`path` 是完整曲库路径 —— 列表里点「在文件夹中显示」直接拿它去 FileStation 就行，不用另查。

同一套规矩下另三个接口（都在自己的 `AudioStation/*.cgi` 上）：

- `Genre.list` v3 → `data.genres`（97 条，含一个空名）、`data.total`
- `Album.list` v3 → `data.albums`，字段 `album_artist` / `artist` / `display_artist` / `name` / `year`（**没有 `id`**）
- `Artist.list` v4 → `data.artists`，字段 `name`（3800 位）

三维度列表落码后的实读（2026-10-15 真机，走 QuickConnect 中继）：艺术家 **3797**（服务端 3800 里滤掉 3 个空名）、专辑 **5752**（5756 滤 4 空名）、流派 **96**（97 滤 1 空名）—— 空名实体显示出来是一行空白，界面统一滤掉，条数与 DSM 差的零头都出在这里。逐页拉满的耗时：艺术家 4 页 **1.0 秒**、专辑 6 页 **2.3 秒**、流派 1 页 **0.3 秒**，串行拉页足够快，不需要并发。

🔴 **曲库库别**：`library=personal` 下流派数为 **0**，`library=all` / `shared` / 不带该参数都是 **97** —— 这个账号的曲库在**共享库**，个人库是空的。

取流：

```
GET /webapi/AudioStation/stream.cgi
    ?api=SYNO.AudioStation.Stream&version=2&method=stream&id=<songID>&_sid=<sid>
```

带 `Range: bytes=0-65535` → **HTTP 206**、`Content-Type: audio/mpeg`、`Content-Range: bytes 0-65535/5316164`。**服务端支持 Range**，拖动进度条有基础。

### 取封面（两条路都验通，按场景选）

🔴 **首选路二（目录里的图片），路一只当兜底**（2026-10-13 用户真机抓到串台后定的）。`cover.cgi` 是按**专辑**在 DSM 的专辑库里找图，而库里同名但不同源的专辑只要都缺 `album_artist` 标签，DSM 就把它们并成**一个专辑实体**、只给一张图：实测专辑名「0」下并了 Low Roar（`/music/Low Roar/2014.0/`）、Superfly（`/music/Superfly/2020.0/`）、林忆莲（`/music/林忆莲/2024.0/`）三家五首，用户看到的就是「不是林忆莲的歌挂着林忆莲的封面」。同轮实测：这三张同名专辑各自的 `cover.jpg` **md5 互不相同**、都取得到（缩略图 8–11 KB / 原图 23–232 KB）；随机 20 个专辑目录 **20/20** 都有 `cover.jpg`。所以跟着曲库的目录约定取图不会串，按专辑名问才会。

**路一 · 按专辑名问 Audio Station**（兜底：目录里没有图片文件时）

```
GET /webapi/AudioStation/cover.cgi
api=SYNO.AudioStation.Cover&version=3&method=getcover
   &album_name=<专辑名>&album_artist_name=<专辑艺术家>&size=small&_sid=<sid>
＋ 请求头 X-SYNO-TOKEN
```

返回 `image/jpeg`，**480×480、30339 字节**。

🔴 **参数必须是 `album_name`。** 把 `id=<歌曲 id>` / `path=<完整文件路径>` / `album=` / `album_artist=` 换上去，一律 **HTTP 404 回 HTML 错误页**。**上一轮 12 首歌逐首用 `id` 要图全 404，是参数名不对，不是「这些文件没有内嵌封面」。**
🔴 这个接口**走标准分发**：带 `api/version/method` 才对，裸打（只给 `id` + `size`）一律回 `code=101`。跟 FileStation 的 `folder_path` 那种「不要套 JSON」的规矩无关。
⚠️ **匹配行为（2026-10-13 实测，同名专辑「0」）**：`album_artist_name` 给**空串**回 200 + 图（DSM 里那张合并实体的 `album_artist` 就是空的）；给**任何非空名字**（林忆莲 / Superfly / 查无此人）都是 **404** —— 这一格填错了不会拿到「别人的图」，是直接没有图。别把空串那次 200 当成「空着也能取到」的好消息：它取到的正是那张被合并的图。
⚠️ `Content-Type` 是 `image/jpeg`，业务错误依旧是 200 + JSON 信封，判「拿到图」要看 MIME。

**路二 · 直接读专辑目录里的图片**（**首选**：曲库一张专辑一个目录、封面是目录里的图片）

```
GET /webapi/entry.cgi               # 先列目录，文件名不固定（这台机上是 cover.jpg）
api=SYNO.FileStation.List&version=2&method=list
   &folder_path=<专辑目录>&limit=100&_sid=<sid>

GET /webapi/entry.cgi               # 小图：120×120
api=SYNO.FileStation.Thumb&version=2&method=get
   &path=<图片完整路径>&size=small&rotate=0&_sid=<sid>

GET /webapi/entry.cgi               # 大图：原图
api=SYNO.FileStation.Download&version=2&method=download
   &path=<图片完整路径>&mode=open&_sid=<sid>
```

实测：缩略图 `image/jpeg`、**120×120、8–11 KB**；原图 `image/jpeg`（样例 600×600、23–232 KB）。
⚠️ **`mode=download` 也回同一份字节，但 `Content-Type` 是 `application/octet-stream`** —— 按 ctype 或扩展名判格式的代码会判错，要原图就写 `mode=open`。
🔴 `folder_path` 必须给**纯字符串**（给 JSON 数组回一整页 HTML，见第四节的坑）。

### 播放：AVPlayer 的三个坎

1. **自签证书**。AVPlayer 直连 `https://IP:5001` → `-1202`（证书无效）。命令行工具里没有可用的信任设置绕过去。
2. **两条可行路线**（都在真实 NAS 上跑通）：
   - **自定义 scheme + `AVAssetResourceLoaderDelegate`** —— 不开本地端口，对沙箱更友好。关键是给 `AVAssetResourceLoadingContentInformationRequest.contentType` 填**正确的 UTI**：`public.mp3`（= `UTType.mp3.identifier`）通过；填 MIME `audio/mpeg` → `-11828`；填错的 UTI（`public.mpeg-4-audio`）→ `-11829`。
   - **本地 HTTP 代理**（`NWListener` 起 127.0.0.1，转发到 NAS）—— 类型信息来自响应头，不用管 UTI。
3. **AVPlayer 判格式依赖 URL 扩展名**。同一份 mp3 字节：`.mp3` 通过，`.bin` / 无扩展名 → `-11828`，`.m4a`（内容仍是 mp3）→ `-11829`。要绕开就用 `AVURLAsset(url:options:["AVURLAssetOutOfBandMIMETypeKey": "audio/mpeg"])` —— 该常量在 SDK 里没有导出的 Swift 名字，用字面字符串当键可用。走 HTTP 路线不需要这个。

🔴 **命令行程序里 AVFoundation 对象必须被强引用**（用一个 `keepAlive: [AnyObject]` 兜住 `AVURLAsset` / `AVPlayerItem` / `AVPlayer`）。只被局部变量持有 → 函数返回即释放 → 播放中途崩。

## 三、改标签（唯一走非公开接口的部分）

⚠️ **2026-10-13 复测：这条通路在这台机上已经打不通了** —— `POST /webman/3rdparty/AudioStation/tagEditorUI/tag_editor.cgi` 回 **403 + DSM 的「页面不存在」错误页**（`_sid` / Cookie / token 三件套都带齐、UA 与 Referer 也补了，仍是 403；`query.cgi` 的 863 个 API 里也只有 `SYNO.AudioStation.Tag` 的只读方法）。下面这套写法是 **2026-10-11 验通过的记录**，要再改标签得先重新探路径。

🔴 **公开接口里没有写标签的能力。** 863 个 API 全量枚举过：`SYNO.AudioStation.Tag` 只有 `getinfo` / `list` 两个只读方法，38 个写方法名穷举全部返回 103；`SYNO.AudioStation.TagEditor` 这个名字不存在。只能走 Audio Station 网页端的内部接口：

```
POST /webman/3rdparty/AudioStation/tagEditorUI/tag_editor.cgi
三件套鉴权：表单 _sid ＋ Cookie id=<sid> ＋ 请求头 X-SYNO-TOKEN
```

### 读

```
action=load
audioInfos=[{"path":"/music/<歌手>/<年.专辑>/<轨道>.<标题>.mp3"}]
```

- `audioInfos` 是**字符串拼接的 JSON**，斜杠原样不转义；路径必须是完整的 `/music/…`（去掉前缀、改用 song id、把键名改成 `filePath` 都读不到）。
- 返回在 **`files`** 里（不是 `items`），字段是：
  `album / album_artist / artist / comment / composer / disc / genre / path / title / track / year`

### 写

```
action=apply
data=[{"audioInfos":[{"path":"…"}],"album":…,"album_artist":…,"artist":…,
       "comment":…,"composer":…,"genre":…,"title":…,"track":n,"year":n,"disc":n}]
```

🔴 **`data` 必须是 JSON 数组，各标签字段挂在数组元素那一层。**

写成对象 → 服务端取 `data[0].audioInfos` 拿到 undefined → **HTTP 502**。两种对象写法（带顶层 `path` / 不带）都是 502，数组写法通过 —— 同一轮里做过对照。

### 判据（这里最容易判错）

- 看 **`files` 回显是否非空**。`success=true` 单独不可信：结构只到「不报错」那一层时（比如完全不给 `data`），服务端会回 `success=true` + `files:[]`，什么都没干。
- 真失败看 `write_fail_files`。

### 写完之后

**索引当场跟上**（实测 0 秒），**不需要额外触发媒体索引重建**。落盘证据：副本文件里出现写入的标记串，ASCII 编码、偏移 21 字节（ID3v2 头 + 帧头之后的位置）。

**非 ASCII 路径同样验通**（2026-10-11）：副本放进 `/music/__tagtest__/<歌手>/` 走同一套 apply，`files` 正常回显带韩文的路径、索引 0 秒更新、字节里出现标记。路径要过两道编码（先拼进 JSON，再整体做百分号编码），两步都没弄坏非 ASCII —— 真实库里 `<歌手>` 这类路径没有例外。

因此「取回原文件 → 本机改 ID3 → Upload 传回 → 重建索引」这条兜底路线不需要了。

**文件操作的码值（官方 API 指南，判读用）**：`400` 参数不合法 · `401` 文件操作未知错误 · `403/404/405` 操作者身份问题 · `407` 操作不允许 · **`408` 路径不存在** · `411` 只读文件系统 · `414` 文件已存在 · `417` I/O 错误 · **`418` 名称或路径非法** · `421` 设备忙。**`408` 与 `400` 的这一对是诊断利器** —— 参数名对、只是文件不在，回 `408`；参数本身不合法，回 `400`。⚠️ **但有例外**：`CopyMove` 对不存在的源不回 `408` 而是直接回 `success` + 任务，这对判据在它身上失效（见第七节）。

**问「这个方法存不存在」的探针**：未登录打 `entry.cgi?api=X&version=V&method=M` —— `119` = 方法存在、只差登录；`103` = 方法不存在；`105` = 权限不足；`102` = **API 名或版本不对**。可以用来快速排除。

⚠️ **但 `102` 的判读不能当结论**：同一批探针在 `PowerSchedule` 上给过「版本不对」，而那个接口其实只是**名字写错了**（真名带 `Hardware.`）。**接口名与版本一律以第七节的 `SYNO.API.Info` 全量清单为准**，别照记忆猜。

## 五、远程链路：QuickConnect 比 Tailscale 快一个量级

外网怎么连，这一节是结论：**用 QuickConnect，不用 Tailscale。**

### 实测对照（同一台 Mac，同一个接口请求）

| 链路 | 落点 | 同一个接口请求 | 取流吞吐 |
|---|---|---|---|
| Tailscale | DERP 美国旧金山 | **2.5 秒** | 16 KB/s |
| QuickConnect | 中继在境内节点（中国移动 AS56046） | **0.15–0.17 秒** | **1.18 MB/s** |

Tailscale 慢不是配置问题：`netcheck` 报 `MappingVariesByDestIP: true`（运营商侧对称 NAT），打洞做不成，只能走中继；30 个 DERP 节点里最近的全在美西（sfo 147ms、lax 154ms、tok 213ms、hkg 232ms），只能选它。

带宽对照组（Mac 直连公网）：国内阿里云源 1.12 MB/s、就近海外 Cloudflare 0.96 MB/s、**美国东岸 14.7 KB/s**。美国东岸那个数和 Tailscale 的 16 KB/s 是同一个量级 —— **瓶颈是跨太平洋那一段被限速**，换任何落在美国的中继都一样，靠调客户端参数解决不了。

### 怎么拿到 QuickConnect 端点

公开解析接口，不需要密码：

```
POST https://global.quickconnect.cn/Serv.php
[{"version":1,"command":"request_tunnel","stop_when_error":false,"stop_when_success":false,
  "id":"mainapp_https","serverID":"<QuickConnect ID>","is_gofile":false,"path":""}]
```

🔴 **中继端点只在 `request_tunnel` 的应答里给**（2026-10-16 实测）。同一天实测
`get_server_info` 的应答已经没有 `relay_dn` / `relay_port` 了，`service` 只剩
`port`(5001) / `ext_port`(0) / `pingpong` / `pingpong_desc`，另加一个 `smartdns` 块：

| 键 | 内容 |
|---|---|
| `smartdns.host` | `<QC-ID>.direct.quickconnect.cn` —— 公网递归 DNS 查它是 **NXDOMAIN**，只有它自己的权威 NS（`ddns-ns*.quickconnect.to`）认 |
| `smartdns.lan` | `<局域网 IP 点换横线>.<QC-ID>.direct.quickconnect.cn` → 解析出局域网 IP |
| `smartdns.hole_punch` | `127-0-0-1.<QC-ID>.direct.quickconnect.cn`（没做成打洞时的占位） |

按旧格式只认 `get_server_info` 的 `relay_dn` 会直接抛错（真机现形：报「QuickConnect
返回了看不懂的内容」，键列表 `["command","env","errno","server","service","smartdns","version"]`）。

🔴 **请求体是数组，QC ID 放在 `serverID`，`id` 是服务名 `mainapp_https`**
（2026-10-12 用假 ID 对照实测：这版回 `errno 4` + `errinfo: Alias not found`，语义正确；
早先记录的「对象 + `svc` + `id` 放 QC ID」那版回 `errno 9` 且 `errinfo` 为空，形状不对。
源码骨架的 `QuickConnectResolver` 按数组版实现）。
`request_tunnel` 对假 ID 同样回 `errno 4`，`errinfo` 带 `request_tunnel.go:62[` 前缀；
`id` 换 `dsm_portal_https` 所得一致，换 `dsm_portal`（http 服务）给的是另一组端口。
🔴 **成功应答也带 `errno: 0`** —— 判断成败只看 errno 非零，别「见 errno 就当失败」
（首连真机时踩过：把 errno 0 当错误报给用户）。

要用的字段（`request_tunnel` 应答）：

| 字段 | 本次实测值 |
|---|---|
| `env.relay_region` | `cn4` / `cn`（境内） |
| `service.relay_dn` | `synr-<区域>.<QC-ID>.direct.quickconnect.cn`（CNAME → `cnrds4.re.cs.quickconnect.cn`） |
| `service.relay_port` | 这台 NAS 专属的中继端口 |
| `service.relay_ip` / `https_ip` | 同一个中继 IP；`https_port: 443` **不是**这条业务 |
| `server.external.ip` | `<公网出口 IP>`（中国移动） |
| `server.interface[].ip` | `<NAS 局域网 IP>`（局域网） |

### 连它的规矩

- 🔴 **必须 https**。那个中继端口只认 TLS：拿明文 http 打上去，收到的是 nginx 的 `400 The plain HTTP request was sent to HTTPS port` —— 这条错误页本身就是证据，说明请求确实被转发到了 NAS 跟前。
- 🔴 **端点用 `relay_dn` 域名，别用 `smartdns.host`**。`relay_dn` CNAME 到 `cnrds4.re.cs.quickconnect.cn`，中继上的 Let's Encrypt 证书按这个名字签，`:relay_port` 走默认校验就能过（2026-10-16 实测 HTTP 200，不加 `-k`）。`smartdns.host` 那个智能域名解析不出结果，而且 `:443` 上证书名字对不上（报 `SSL: no alternative certificate subject name matches target host name`）。**这跟 Tailscale 那条正好相反** —— 那条连的是 NAS 自己的自签证书，客户端必须放行。
- IP 写法（`<中继 IP>:<relay_port>`）同样通，但要关证书校验。要稳就用域名写法。
- **端点会变**：中继 IP、端口、`relay_dn` 都是解析接口给的，每次启动重新问一遍，别写死。
- `relay_port` 是这台 NAS 专属端口；`https_port: 443` 那个不是这条业务（实测打不通）。

### 中继上的完整体验（`play-bench`，2026-10-11 21:22 实测）

| 指标 | QuickConnect 中继 | Tailscale 对照 |
|---|---|---|
| ping | **16 ms** | 314 ms |
| 登录 | **754 ms** | 1864–3525 ms |
| 曲库请求（500 首） | **495 ms** | **140,865 ms**（2 分 21 秒） |
| 取流第一段 64KB | **99 ms** | 3835 ms |
| 取流吞吐（4 段共 1MB） | **1.18 MB/s** | ~16 KB/s |

播放（路线 A，本地 HTTP 代理）：

- 准备 559 ms，**起播 152 ms**
- 播放 20 秒，游标推进 19.9 秒（推进/墙钟 0.99），**卡顿 0 次**
- 拖动到 50% / 90% / 30%：恢复出声 **115 / 123 / 114 ms**
- 连拖 5 次（间隔 0.2 秒）松手后 **1056 ms** 恢复 → 进度条要做「松手才真跳」

路线 B（自定义 scheme + resourceLoader）起播 103 ms，但**准备要 4234 ms** —— 它把整份 5.3MB 一次代答完（5.3MB ÷ 1.18MB/s ≈ 4.5 秒）。**要流式就用路线 A。**

**结论：远程播放与本地没有可感差别。** 320kbps 音频只需 40 KB/s，这条链路给了 1.18 MB/s，是 30 倍余量 —— 架构里不需要预取，也不需要本地缓存。

⚠️ 一处要留意：AVPlayer 对 mp3 是**一次性请求整份文件**（`Range: bytes=0-5316163`），不是按需分段。5.3MB 的歌 4.3 秒拉完无所谓；换成 60 分钟整轨音频（约 140MB）就要两分钟，那类素材要另想办法。

### 顺带量到的

- Mac 到中继的 ICMP 往返 **16 ms**（境内节点，往返低）；一个完整 HTTP 请求（到 NAS 再回来）0.13–0.17 秒。**两个数要分开看** —— 单看 16 ms 会误判成「在局域网」。
- 手机 DS Music 填 QC ID、走流量听歌偶尔等一秒左右 —— 与「中继落在境内」一致。

### 另外两条路（都不通，记下来省得再试）

- **公网 IPv4 直连**：`<公网出口 IP>:5001` 超时、`:5000` 回 502 —— 没有端口映射，也没有公网 IPv6（`external.ipv6` 是 `::`）。
- **走局域网**：NAS 在 `<NAS 网段>`、Mac 在 `<Mac 网段>`，不是一个网段。那一轮 `<NAS 局域网 IP>` 回了 200 但花了 2.5 秒 —— 是绕 Tailscale 网段路由过去的，不是局域网。

### 1. 文件管理 —— 一通百通，写法定死

```
POST /webapi/entry.cgi
api=SYNO.FileStation.List&version=2&method=list
   &folder_path=/music          ← 🔴 纯字符串，别给 JSON 数组
   &additional=["size","time","type"]&offset=0&limit=100
   &sort_by=name&sort_direction=asc&_sid=<sid>
＋ 请求头 X-SYNO-TOKEN
```

- 🔴 **`folder_path` 给 JSON 数组（`["/music"]`）→ HTTP 502 回 HTML 错误页；给纯字符串 → 正常。** 12 组参数交叉打过、关键组重复 3 次，结果稳定 —— 与参数顺序无关。
- 🔴 **`additional` 反过来只认 JSON 数组**（2026-10-11 实测）：给逗号串 `size,time,type` **被静默忽略**，条目只剩 `isdir` / `name` / `path`。本文档此前那句「数组或逗号串都行」是错的。
- 条目字段（`additional` 数组给全时）：顶层 `name` / `isdir` / `path`；`additional` 里 `size`（目录不给字节数）/ `time`（**字典** `{atime,crtime,ctime,mtime}`，Unix 秒）/ `type`（**大写扩展名**，如 `JPG` / `MP4` / `MP3`；**目录为空**）/ `owner` / `perm` / `real_path` / `mount_point_type`。
- **分类型、选图标、决定操作菜单都靠 `additional.type`**（转小写再比对），不要自己从文件名切扩展名。
- 分页 `limit=100` 正常（`/music` 下 total=3621）。逐级浏览通。`list_share` 通（8 个共享文件夹：docker / homes / music / photo / video / <共享夹> / <共享夹> / <共享夹>；条目在 `shares` 键下）；`getinfo` 通。`DirSize.start`、`Search.start` 都收 taskid —— 搜索能顶替浏览，**但 `Search` 有假空与过程值两个坑，动手前先看本节末那一段**。
- 🔴 **个人目录是 `/homes/<用户名>`，不是 `/home`**（`/home` 回 `code=408` 路径不存在）。

**排序字段（`sort_by`，2026-10-14 实测）—— 服务端只认三个**

| 项 | 结果 |
|---|---|
| 被认的 | **`name` / `size` / `mtime`** 三个 |
| 不认的 | `time` / `type` / `owner` / `posix` / `real_path` / `filename` / `atime` / `ctime` / `crtime` / `user` / `group` —— 静默退回按名字排，**不报错** |
| `sort_direction` | `asc` / `desc` 都生效 |

- **`size` 要在有文件的叶子目录里才验得出来**：`/music` 顶层全是目录，而目录的 `size` 是**它自己那一项的大小**（实测 176 这种），不是内容合计，所以在顶层看 `size` 排序像是没生效。换到叶子目录逐项比对，asc 非递减、desc 非递增，完全正确。
- **混合目录 desc 会把整段反转**：asc 时目录恒在前（服务端自己分过组），desc 时文件跑到目录前面。按服务端原序呈现，客户端不再分组。
- 未知值静默忽略，所以「点了没反应」只能靠与默认序对比才发现 —— 探针 `experiments/shuffle-lab/fileprobe2.py`（14 个候选逐个试）。

**分页上限**：`limit=5000` 服务端照收（`/music` 顶层 3621 项一次拿全）。列表按 1000 一页拉。

**系统目录与 `total`**：`#recycle` / `@eaDir` 这类以 `#` / `@` 开头的条目与普通目录**混在同一层**，且**算在 `total` 里** —— 界面把它们藏掉之后，拿藏过的条数去比 `total` 会永远差那几项、一直以为还有下一页；分页判据要另记一把「服务端返回过的条数」。

**可写性**：`additional.perm.acl.write`（Bool，实测在 `perm.acl` 下），条目与共享夹（`list_share`）都给。写操作那批拿它把不可写的目录灰掉。

**缩略图（`FileStation.Thumb` v3 `get`，参数 `path` + `size` + `rotate`）—— 哪些类型出图**

**`Upload` 定稿写法**（15 种写法单变量对照，8 通 7 败，结论唯一）

```
POST /webapi/entry.cgi?api=SYNO.FileStation.Upload&version=2&method=upload&_sid=<sid>
请求头：
  X-SYNO-TOKEN: <synotoken>
  Content-Type: multipart/form-data; boundary=<边界>

body（段序固定：字段在前，file 段最后）
  --<边界>  name="path"             值 = 目的目录
  --<边界>  name="create_parents"   值 = true
  --<边界>  name="overwrite"        值 = true
  --<边界>  name="file"; filename="x.txt"  ＋ 文件内容
  --<边界>--
```

六条硬约束，每条都有单独一组反例（括号里是它回的错误码）：

- 🔴 **`path` 必须放 multipart body，不能放 query**（放 query → `401`）。**这是此前 `401` 的真因** —— 与中继无关（Tailscale 直连一样 401），也不是 multipart 拼错。
- 🔴 **每个 part 不能带 `Content-Length` 头**（带 → `401`）。
- 🔴 **顶层 `Content-Type` 不能带 `; charset=utf-8`**（带 → `401`）；与群晖社区那条老结论一致。
- 🔴 **`X-SYNO-TOKEN` 必须带**（不带 → `119` SID not found）；放 query 的 `SynoToken` 也认。
- 🔴 **`_sid` 只在 query（或 Cookie `id=`）里给，不能当 body 字段**（当字段给 → `119`）。
- **版本 2 或 3 都行；v1 回 `104`**（版本不支持）。

🔴 **段序同样是硬约束：字段在前、`file` 段最后。** 反过来（file 段排在最前面）服务端**根本不回响应**，客户端一直等到自己超时 —— 上一轮 8 次 90 秒超时、累计 12 分钟就是这类写法堆出来的。这与浏览器实际发出的段序一致（`path` → `create_parents` → `overwrite` → `_sid` → `file`）。
🔴 **前三条失败时服务端会先等约 10 秒再回码**（`401` 实测 10.2 秒），排查时别把它当成网络慢。

**`CopyMove` 定稿写法（2026-10-12 实测确定）**

```
POST /webapi/entry.cgi?api=SYNO.FileStation.CopyMove&version=3&method=start&_sid=<sid>
＋ 请求头 X-SYNO-TOKEN

  path=["…/源"]                  ← 要复制的源（数组或纯字符串都给）
  dest_folder_path="…/目的目录"    ← 🔴 目的目录的参数名
  remove_src=false               ← true = 移动（复制 + 删源）
  overwrite=true

→ {"data": {"taskid": "FileStation_…"}, "success": true}
```

- 🔴 **目的目录的参数名是 `dest_folder_path`，不是 `dest_folder`。** `dest_folder` 在 **v1 / v2 / v3 上一律回 `400`**（Invalid parameter of file operation）；`dst` / `destination` 同样不行，源用 `src_list` 也不行。14 组单变量对照只留下这一个。
- 三处独立验证：只读矩阵里只有 `dest_folder_path` 那组回 `success` + `taskid`，其余 11 组全 `400`；沙箱里真复制成功（`_dst` 下出现了复制过去的目录）；同一个形态用 `remove_src=true` 真移动一次也成功。
- **任务式**：`start` 只回 `taskid`，成败靠 `CopyMove` 的 `status` 轮询到 `finished`。
- 🔴 **`start` 对不存在的源路径照样回 `success` + `taskid`** —— 点对点应答只证明「参数合法」，不证明「复制成功」。**判成败必须看任务状态**。对比：`Delete` / `Rename` 会把真因写在 `error.errors[]` 里，`CopyMove` 不写。
- 定位 `400` 的通用办法：**拿一个不存在的源路径去打** —— 参数名错会停在参数校验回 `400`，参数名对就往下走。可以在不写任何东西的前提下筛掉错的参数名。⚠️ 原以为判据是「名字对回 `408`」，实测 `CopyMove` 连不存在的源都回 `success`，所以判据实际退化成「**400 = 名字错，非 400 = 名字对**」，别的接口要单独看。


`additional.type` 对非媒体文件也给（`INI` 等），但**缩略图不给图**（txt / ini 都回 404）。

**可写性怎么判（2026-10-12 定）**

- ✓ **用 `perm.acl.write`**：`FileStation.List` 的每条条目、以及 `list_share` 的每个共享夹，`additional.perm` 里都带 `acl.write`（配 `is_share_readonly` / `share_right` / `posix`）。实测 8 个共享夹全是 `RW`、`acl.write=true`（账号是管理员）。
- ✗ `CheckPermission` 弃用：`write` / `check` 两种方法 × `path` 数组与纯字符串 × 各种额外参数，**七种形态全回 `401`**，有一次还直接回了 HTML 错误页。
- ✗ `CheckExist` 弃用：`file` / `dir` / `exist` / `exists` / `check` / `check_exist` / `status` 七个方法名 × 两个版本都不通（`check` 认得方法，但参数怎么给都回 `400`）。**查文件是否存在改走 `List` 比对文件名**。

**搜索（`FileStation.Search` v2）—— 三个状态必须分清**

`start` → `taskid` → `list` 轮询 → `stop`。`start` 的参数：`folder_path`（串或数组都给）/ `pattern` / `recursive`。**难点全在 `list` 的三种应答上**：

| 应答 | 含义 | 该怎么办 |
|---|---|---|
| `{files, offset, total, finished:false}` | **任务还在跑**，`total` 是「已索引到多少」的过程值 | 继续轮询；这时就能先显示部分结果 |
| `{total, files, finished:true}` | **任务跑完**，这个 `total` 是终值 | 取它当结果数 |
| `{finished:true}`（**连 `total` 键都没有**） | 🔴 **假空** —— 服务端这次什么都没给，不是「0 条」 | `stop` 掉重来，一般重试 1~5 次就出 |

- 🔴 **假空与真零要分清**：真零是 `{"total": 0, "finished": true}`（有 `total` 键）。`flac` / `m4a` / `lrc` 查出来就是这种真零。
- 🔴 **`total` 不能拿第一次的**：同一个查询（`pattern=mp3` @ `/music`）在一小时里给过 5110 → 10230 → 12328，那是索引还在建。**必须轮询到 `finished=true` 再取**，实测四轮稳定给 **12328**。
- **重试成本很低**：假空在第一次轮询（约 0.8 秒）就看得出来，不必把窗口等到超时。第一轮实测「一次完整搜索」平均 2.9 次 `start`、4.0 秒，最坏 5 次、6.9 秒；**2026-10-14 复测最坏连吃 6 次**假空才出结果（`dirsearch4.py` G5）→ **重试上限取 12**。
- **`pattern` 是文件名子串匹配**：不吃通配符（`*.mp3` 回 0），大小写不敏感（`MP3` = `mp3`），带点不带点一样（`.mp3` = `mp3`）。所以按扩展名筛要自己再过滤一遍 —— `ape` 会命中山寨 `Shape.mp3`。
- **`recursive` 要真递归就得配数组**（老结论）与**给串也行**（新实测）两条都出现过，实际是同一个假空在捣乱；`folder_path` 数组 + `recursive=true` 是稳的写法。
- 实测分布：`/music` 下 **mp3 = 12328**（≈ 曲库的 12331，**曲库就是 `/music`**；Audio Station 第一页 1000 首的路径全在 `/music`）；`wav` 21 · `ape` 39 · `wv` 13 · `ogg` 3 · `aac` 2 · `wma` 1（这几个是子串计数，偏高）；`flac` / `m4a` / `aiff` / `png` / **`lrc` 都是真 0**。
- 🔴 **`lrc` 真 0 ⇒ 库里没有歌词文件**，再叠上歌词抽样 12 首全空 → **歌词面板本期不做**（`SYNO.AudioStation.Lyrics` 接口本身是通的，回 `{"lyrics": ""}`）。
- 根目录 `['/']` 拿不到（试满 12 次都假空）；**给全部共享夹的数组**能拿到数。搜索范围建议直接传具体目录数组。

**两处写行为的订正（2026-10-12，用 `Download` 读回内容核对）**

| 动作 | 早前结论 | 实测 |
|---|---|---|
| 上传同名 + `overwrite=false` | ~~直接覆盖~~ | 🔴 **回「成功」但内容不变**（静默跳过）。新文件 + `overwrite=false` 正常写入 → **这个参数只对同名生效，且不报冲突** |
| `Rename` 撞名 | ~~直接覆盖成功~~ | 🔴 **回 `1200` + `errors:[{code:414}]`，两个文件都在**。`path` 给数组或纯字符串都一样 |

→ 结论：**改名的冲突可以交给服务端拦；上传的冲突必须自己先查**（`List` 比对文件名），因为上传那条回的是「成功」。

**写操作的收口实测（2026-10-14，`experiments/shuffle-lab/fswrite9.py` + `fswrite10.py`）**

全在 `/homes/<用户>/DreamanualWriteCheck_<时间戳>` 沙箱里跑、跑完自删。判据一律是**读回内容或 `List` 核对真实条目**，不看返回码（`start` 的点对点应答只证明「参数合法」）。

`CopyMove`（复制 / 移动）

| 情形 | 实测 |
|---|---|
| 撞名 · 文件 · `overwrite=false` | **跳过**，目标原内容没动。🔴 任务仍报 `finished=true`、**不带 `errors`** |
| 撞名 · 文件 · `overwrite=true` | 真覆盖（读回源内容） |
| 撞名 · 目录 · 两个值 | **一律合并**（源目录内容并进目标同名目录）—— `overwrite` 只管文件 |
| 移动撞名（`remove_src=true` + `overwrite=true`） | 源删掉、目标被覆盖 |
| 源在目标内部 / 源与目标的同名项是同一个 | **静默跳过**：不报错、也不生成 `a(1).txt`。界面必须自己禁用这种目标 |

`weekdays` 是逗号分隔的 0–6，**0 是周日**（从「9:00 排 `1,2,3,4,5`、10:30 排 `0,6`」这对组合推断 —— 工作日 / 周末的分法）。

**`save` 的形状（2026-10-17 实测，`psprobe.py`）**

- 🔴 **两个字段各是一个 JSON 数组串**：`poweroff_tasks` 与 `poweron_tasks` 都传
  `[{...}]` 序列化后的字符串（表单字段、URL 编码），幂等回写后**回读与原样逐字一致**。
  `weekdays` 在串里必须是**逗号串**（`"2,3,4,5"`），不是数组。
- 🔴 **`weekdays` 上界 = 6**：`"0,1,2,3,4,5,6"` 服务端原样收下（0 = 周日、6 = 周六，
  与上面的工作日 / 周末配对吻合）。
- 🔴 **非法星期被静默剥掉**：给 `weekdays: "7"` 时 `save` **照回 `success`**，
  但那条任务回读的 `weekdays` 是**空串** —— 条目还在，成了「未设星期」的垃圾任务。
  界面上绝不能产出 6 以外的数字；判存成功要看**回读**，不能看 `save` 的返回值。
- **`poweroff_tasks` 收多条**：实测一次落 2 条都在 —— 关机计划没有「只能一条」的
  服务端限制（DSM 界面给不给排多条是另一回事）。
- 客户端写回按「读到的原样拆回两组、各组保持服务端次序」实现，不做重排。

**增删不需要额外字段（2026-10-17 实测，`psprobe2.py`）**

- **新增**：一条任务就四个键（`enabled` / `hour` / `min` / `weekdays`），**没有任务号、
  也没有名字** —— 往数组里追加一项写回即可，`poweroff` / `poweron` 两组都验过，
  追加后服务端照单全收、回读在列。
- **删除**：`save` 是**整表覆盖** —— 把数组里某条去掉写回去，那条就没了。
  从 8 条删回 1 条验证过，回读与原样一致。
- **条数上限**：`poweroff_tasks` 一次追加到 8 条服务端照收，本次实测范围内没触顶。

- **开机（NAS 已关机时唤醒）纯软件做不到**：QC 解析接口不给 MAC，`SYNO.Core.Network.WOL` 只有 `wake`（唤醒别的设备）；本机在 `<Mac 网段>`、NAS 在 `<NAS 网段>`，不同广播域。**交给 NAS 自己的开机计划。**

### 6. 2026-10-14 补测（接界面这一批，探针 `sysprobe/2/3.py`）

把第 1–4 节的字段接上界面之前，把每个数**拿实测钉了一遍单位**：

- 🔴 **CPU 两套数单位不同**：`user_load` / `system_load` / `other_load` 是**百分比**（DSM 的「利用率 = 用户 + 系统」，`other_load` 即 I/O 等待）；`1min_load` / `5min_load` / `15min_load` 是**平均负载 × 100**。判据：三个并发 `DirSize` 压测下 `1min_load` 从 108 爬到 **246**，两核机器上不可能是百分比；而 `user_load` 全程 21–29。对表：0.28 的利用率 ↔ 1.10 的平均负载（R1600 是 2 核 4 线程）。**解码要除以 100。**
- 🔴 **`read_byte` / `write_byte`（含 `network.rx/tx`）是字节/秒，不是累计值**（10-12 那轮「读数在 10^10 量级 → 累计值」的判断是错的，同一份日志里第二次采样比第一次小，累计值做不到）。判据：客户端限速 ~1.5 MB/s 下载，同一时刻 `space.total.read_byte` ≈ 3.1 MB/s、盘 `sata1` ≈ 10.8 MB/s，与已知速率同一量级。**界面直接显示速率，不用自己再除。**
- 🔴 **`up_time` 分与秒不补零**：实测 `"11:1:0"`、70 秒后 `"11:2:16"`。10-12 记的 `5:27:13` / `10:56:51` 恰好全是两位数，按定长切必错 → 按冒号分段各自解析。小时段累计不回绕（DSM 信息中心按天显示）。
- `volumes[]` **没有 `display_name`**，界面名从 `num_id` 拼（DSM 中文叫「存储空间 N」）；`disks[]` **没有 `used`** —— 单盘已用量服务端不给（SHR 下盘也不是独立卷），「每盘一条进度条」落不了地。
- 🔴 **卷名两边差一个下划线**：`Storage` 给 `id=volume_1`，`Utilization` 的 `space.volume[]` 给 `display_name=volume1` —— 按 `id` 配永远配不上，按 `volume<num_id>` 配。
- `Core.System.Process` v1 `list` 可用（418 条，`sort_by=cpu&sort_direction=DESC` 认），单进程 `cpu` 是百分比（`synoavscan` 249 = 双线程扫两个核）。
- `Core.System.info` 连发 10 次零失败（1.1 秒）—— 频繁轮询没有压力，保活心跳本来就是它。
- `PowerSchedule` **只有 v1**（v2 / v3 回 104；`SYNO.API.Info` 里 `maxVersion:1`）。`load` 读到现成计划：开机两条（工作日 9:00、周末 10:30）、关机一条（周日–周四 0:30）。**`save` 与 `shutdown` / `reboot` 至今没执行过** —— 真关机要挑时间单独验，不能顺手点。
- `SYNO.API.Info query=all` 863 条里**没有任何 shutdown / reboot 字样的接口** —— 这两个方法只能对 `SYNO.Core.System` 盲试，别照接口清单猜。

## 十一、原文件下载（2026-10-13 实测，只读）

右键「下载」走这条：`SYNO.FileStation.Download` v2 `method=download&mode=open`。
两个探针 `downloadprobe.py` / `downloadprobe2.py`（都只读，样本落 `/tmp`）。

### 1. 曲库那条 `path` 直喂即可

`AudioStation.Song.list` 回的 `path`（形如 `/music/<歌手>/<年.专辑>/<曲>.mp3`）直接当 FileStation 的 `path` 用，不用再换算 —— 与「在文件夹中显示」同一条路。实测一首 5,316,292 字节的 MP3 完整拿回。

### 2. `mode` 不校验，只影响 MIME

| `mode` | HTTP | `Content-Type` | 字节数 |
|---|---|---|---|
| `open` | 200 | `audio/mpeg` | 5,316,292 |
| `download` | 200 | `application/octet-stream` | 5,316,292（与 open 逐字节一致） |
| `bogus`（瞎写一个） | 200 | `audio/mpeg` | 一样拿回 |

按「取流用 open」的惯例写 `open` 就行；写错也不报错，**别拿它判成败**。

### 3. 应答头 —— 进度条与断点续传的原料都在

`Content-Length` 有（能报百分比）、`Accept-Ranges: bytes` 有（能续传）、`ETag` / `Last-Modified` 有。**没有 `Content-Disposition`** —— 存盘文件名得自己拼。

### 4. 🔴 失败有两种形状，装不进同一条判据

| 触发 | HTTP | 应答 |
|---|---|---|
| 会话问题（缺 `_sid` / `_sid` 无效 / `_sid` 与 token 不配对） | **200** | `application/json`，`{"error":{"code":119},"success":false}` |
| 路径问题（不存在 / 是目录 / `path` 参数整个缺省） | **404** | `text/html`（DSM 自带 404 页，11,939 字节，**不是** JSON） |

判成败要**两条都写**：先认「回来的是 JSON」为失败（会话类），再认「非 2xx」为失败（路径类）。只看状态码 → 会话过期时会把 JSON 存成 `.mp3`；只看 MIME → 404 那页 HTML 也会存成 `.mp3`。

### 5. 🔴 这条接口不认「会话名」，认的是「`sid` 与 token 配不配对」

原本照第一节的规矩推：「文件接口得用文件会话那把钥匙（`session=FileStation`），用音频那把回 105」。实测不成立 —— 同一首歌、`path` 故意给目录 `/music`（好把「认证不过」与「路径不对」两个分支分开）：

| `_sid` | `X-SYNO-TOKEN` | 结果 |
|---|---|---|
| 文件会话 | 文件会话（配对） | 认证通过（回 404，卡在路径分支） |
| 音频会话 | 音频会话（配对） | **认证通过**，文件完整拿回 |
| 文件会话 | 音频会话（配错对） | `119` |
| 文件会话 | 不带 | `119` |
| 不带 | 文件会话 | `119` |

**AudioStation 那把钥匙配自己的 token 一样能下载**（第一探里这条最初被当成「偶然」，第二探发现是探针把两把钥匙的 `sid`/`token` 交叉取了；改对之后复验仍通）。分接口用各自会话是「按归口写」的工程规矩，不是这台 NAS 的硬校验 —— 它只查 `sid` 与 `X-SYNO-TOKEN` 是一对。

⚠️ **同一个「配错对」，码随接口变**：AudioStation 类接口回 `105`（第一节实测），`FileStation.Download` 回 `119`。写错误提示时别把两处并成一个码。

### 6. 中继上的速度

QuickConnect 中继实测约 **0.5 MB/s**（一首 5.3 MB 约十秒出头）。下载要有进度反馈，别做成点了没声响。
