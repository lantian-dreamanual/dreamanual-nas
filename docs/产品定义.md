# Dreamanual NAS 助手 · 产品定义

立项 2026-10-12。本文是功能范围的单一来源；接口怎么调见 [接口结论](接口结论.md)。

## 一、定位

连接群晖（Synology）NAS 的 macOS 桌面客户端，以**听自己的曲库**为主轴，兼顾文件管理与开关机。

明确排除的三块，避免范围蔓延：

| 不做 | 原因 |
|---|---|
| 相册 | 接口只能按目录树浏览，共享空间没有「相册」接口，做不了按相册分组；使用频次也最低 |
| 系统状态 / 套件中心 / 控制面板 | 已有一个第三方同名应用覆盖这些，且不是常用项 |
| 在线音乐 | 曲库来源就是 NAS，不做在线曲库服务 |

## 二、地基（所有模块共用）

- **连接**：输入 QuickConnect ID，每次启动重解析端点（`global.quickconnect.cn/Serv.php`），外网自动走中继。可选填直连地址（局域网或 Tailscale）覆盖默认路由。
- **口令**：存 macOS 钥匙串，不落配置文件、不落日志。
- **双会话**：文件 / 系统 / 相册走 FileStation 会话，曲库走 AudioStation 会话。`sid` 与 `SYNO-TOKEN` 必须成对，配错对会被判成会话无效（AudioStation 类接口回 `code=105`，`FileStation.Download` 回 `119` —— 码随接口变，见 `接口结论.md` 第十一节第 5 条）。
- **保活**：定时心跳；失效时自动重登并重放当前请求。
- **外壳**：侧栏（三个模块 + 设置）+ 主区 + **底部常驻播放条**，切到任何页面播放都不中断。

## 三、模块一 · 听歌

**浏览（四维）**

- 全部曲目 12331 首
- 艺术家 3800 / 专辑 5756 / 流派 97
- 列表同一次请求就带回流派，不需要为每行再发请求
- 三个实体维度的列表 —— ✅ 真机点验（2026-10-15；艺术家 3797 / 专辑 5752 / 流派 96，与服务端条数的差全是滤掉的空名；切换 0.3–2.3 秒；点一行代入筛选回表，页头亮条件名 + 清除筛选 + 分段落在对应项）

**表头（曲库表）**

- 点表头按该列排、同一列再点换方向；表头可拖动改列序（拖动中的列画虚线框与手柄、落点亮主色竖线；标题列钉首位、不可拖也不当落点）
- 表头最右竖三点配字段的显隐；排序与列序都存本机、跨重启保留

**播放**

- 取流有两条路（`AudioStation/stream.cgi` 与 `FileStation.Download`），都支持 `Range` → HTTP 206
- 播放 / 暂停 / 上一首下一首 / 进度拖动 / 音量
- 播放模式与队列（顺序 / 单曲循环 / 随机）
- **键盘**：空格播放 / 暂停、← / → 后退 / 前进 5 秒（本地事件监听，搜索框里打字不受影响）
- **系统媒体键**：Mac 的 F7 / F8 / F9、控制中心、AirPods 按压走 `MPRemoteCommandCenter`，并把曲目信息发布到控制中心（不自己绑 F8，理由见设计规范第八节「键盘与系统媒体键」）

**右键**

- 曲库表与队列表的歌曲行右键：播放 / 下一首播放 / 评分 / **下载原文件**
- 下载走 `FileStation.Download` `mode=open` 取**原文件**（不是转码流），先弹保存面板挑位置；中继上约 0.5 MB/s，落盘后给一条 Toast

**歌词**

- 优先读文件内嵌（`Lyrics.getlyrics` 读的是 MP3 的 USLT 帧；全库覆盖约 0.3%，实测 880 vs 879 字对照确认）
- 没有内嵌就走在线搜索兜底（`LyricsSearch.searchlyrics`，服务端装插件后可用，回多候选、含时间轴）
- 沉浸模式歌词空态显示「未匹配到歌词」+ 下一首条目（可点跳转）。接口行为详见 `接口结论.md` 第八节

**详情与编辑**

- 详情面板：时长 / 码率 / 采样率 / 格式 / 大小
- **改 ID3 标签** —— 唯一走非公开接口的部分，写的是 NAS 上的真实文件
- 右键「在文件管理中显示」，跳到文件管理模块的对应目录

**不做**：在线封面补全、曲库导入导出。

## 四、模块二 · 文件管理

**浏览**（只读那批 2026-10-14 已落：目录树 + 面包屑 + 文件表 + 排序分页 + 缩略图 + 下载）

- 共享文件夹导航（实测 8 个）+ 目录树 / 面包屑 —— ✅ 已落（树按名称正序逐级懒加载，一层先列 8 个、其余收成「还有 N 个」；面包屑最后一段不可点）
- 列表带大小与修改时间，支持排序与分页 —— ✅ 已落（排序交给服务端；实测服务端只认 `name` / `size` / `mtime` 三个字段，界面就只给这三列、列序固定）
- 搜索 —— ✅ 已落（2026-10-14；**提交式**：回车才发请求，服务端假空自动重试、上限 12 次并显示「第 N 次」；结果分页懒加载、点结果跳回所在目录并选中。**没做「输入即筛」** —— 每次搜索要 2–9 秒，输入即搜会把每个键变成一次全库遍历）
- 图片缩略图、下载 —— ✅ 已落（`Thumb` v3 图片与视频出图、音频与非媒体回 404 退回类型图标；下载走 `Download mode=open` 取原文件）
- 目录大小（`DirSize`）—— ✅ 已落（2026-10-14；**按需触发、一次只算一个**：右键菜单「计算大小」，算出的体积进列表大小格与状态栏合计；没算的目录在状态栏标「N 个文件夹未计」。理由见第七节）
- 多选与勾选框 —— ✅ 已落（2026-10-14，随单文件写操作那批：勾选列 + 表头全选半选，Cmd 加选 / Shift 范围 / Cmd+A 全选；刷新后清掉不在列表里的选中）

**写操作**（完整文件管理器）

- 新建文件夹 —— ✅ 已落（2026-10-14；建前先查重名，服务端重名回「成功」靠不住）
- 上传（支持一次请求传多个文件；同名处理见第七节）—— ✅ 已落（2026-10-14；工具条「上传」与拖入两条入口、一批多项、上传行常驻列表上方带速率与进度与取消、撞名三选弹窗、「应用于全部 N 项」。上传文件夹是客户端先 `CreateFolder` 再逐个传，空目录单独建一条）
- 改名、删除 —— ✅ 已落（2026-10-14；改名走 JSON 数组参数、重名服务端拦（`errors[414]`）；删除一律 `recursive=true`、异步任务轮询，**成败看任务的 `errors[]` 不看 `finished`**，确认弹窗列清单、危险色按钮）
- 复制、移动 —— ✅ 已落（2026-10-14；工具条与右键菜单两个入口，各自弹一次选目标；异步任务 + 轮询报结果）
- **复制 / 移动走「选目标弹窗」**：搜索框输入即筛选（平铺结果、每行带完整路径）+ 树形浏览逐级懒加载（每展开一层才拉一层，`sort_by=filename` 升序）；默认目标为当前所在目录；目标等于来源或为其子目录时禁用确认；确认后走异步任务轮询报结果。两千多个兄弟文件夹的定位靠搜索，不靠滚动。✅ 已落，**一处按实测改了做法**：搜索是**客户端过滤树里已拉过的层**，不走 `FileStation.Search`（那条路实测连着假空，驯服它留给搜索那批）。弹窗打开时先把当前目录那一层拉满，`music` 那种三千多个兄弟目录的场景因此开箱可搜 —— 正好是原型说痛的那个场景
- **同名冲突的处理按接口能做什么给**：上传三选（替换 / 保留两者 / 跳过），多选或批量时多一个「应用于全部 N 项」；**复制 / 移动只有两选（替换 / 跳过）** —— 接口不能给新来的那一份改名（`CopyMove` 的 `name` 一族全被忽略），「保留两者」只剩「给目标处已有的那一项改名」，会把「2」贴到用户原来的文件上，不做。冲突必须在客户端先判 —— 上传 `overwrite=false` 撞名回「成功」但内容不变，服务端不报
- **「跳过目录」靠客户端不发那一项**：服务端对撞名目录一律合并，`overwrite=false` 表达不出「跳过」；另外 `skipstatus` 只说明「这批里有同名项」，不是跳过的判据（目录撞名也带它）
- **删除确认写明不可恢复**：删除不进回收站（实测），文件夹要标出「含 N 项」，确认按钮走危险色
- 可写性判定读 `perm.acl.write`（`List` 或 `list_share` 的 `additional`），不可写的目录把写操作灰掉 —— ✅ 已落（共享夹一层首选、其次父层树缓存，取不到乐观当可写；不可写时出通栏提醒条、工具条四个写操作全灰）

> **接口侧已收口**（2026-10-14，细则见 `接口结论.md` 第七节第 1 条末）。六条会改界面做法的：
> ① 撞名的「跳过」服务端**不报错**（任务照报 `finished`）→ 冲突必须客户端先判；⚠️ **不能拿 `skipstatus` 当跳过判据** —— 它只说明「这批里有同名项」，撞名的目录照样带它而内容是合并了的；
> ② **目录撞名一律合并**，`overwrite` 只对文件起作用 → 复制 / 移动的「跳过目录」靠客户端不发那一项；
> ③ **`CopyMove` 不能给新来的一份改名**（`name` / `new_name` / `rename_to` 全被忽略）→ 「保留两者」只有上传能做；
> ④ **重名建夹服务端回「成功」但什么也没做** → 建夹前必须自己查重名；
> ⑤ **上传文件夹要先 `CreateFolder` 再逐个传**（上传的 `filename` 不能带斜杠，回 `418`）；
> ⑥ 删目录一律显式给 `recursive=true`（不给＝递归删），**失败藏在任务 status 的 `errors[]` 里**。

## 五、模块三 · 关机与计划

- 状态卡片：型号 / DSM 版本 / 温度 / 运行时长 / 内存 / CPU / 每盘读写

## 七、从实测来的硬约束

下面这些不是设计偏好，是接口行为决定的。写代码时必须照做，否则会出现「看起来成功、其实没做成」：

| 约束 | 依据 |
|---|---|
| 上传必须有进度条与取消 | 上行吞吐只有 0.31–0.32 MB/s（下行是 1.18 MB/s），传 50 MB 要约 2.6 分钟 |
| 上传前自己查重名 | `overwrite=false` 传同名文件回「成功」但内容不变，服务端不报冲突 |
| 上传文件夹要先建目录、再逐个传 | 上传的 `filename` 不能带斜杠（回 `418`），一个请求只有一段文件；空目录没有文件能带着它上去 |
| 改名冲突交给服务端拦 | `Rename` 撞名回 `1200` + `errors[414]`，两个文件都还在 |
| 删除确认要写明不可恢复 | 删除不进回收站 |
| 复制 / 移动的成败等任务状态 | `CopyMove.start` 对不存在的源路径也回 `success` + `taskid`，只看它会失败报成成功 |
| 搜索带重试、轮询到 `finished=true` | 服务端随机返回假空（应答里连 `total` 键都没有）；`total` 是已索引条数的过程值，不是结果数。实测最坏连吃 6 次假空 → 重试上限取 12 |
| 目录大小按需算、一次只算一个 | `DirSize` 是异步任务且很慢（`/music` 整树实测 29 秒）；`path` 给多条只回**一个合计值**，分不出各自的体量 |
| 目录大小的任务号会坏掉，要丢号重来 | `status` 回 `599` 表示这个任务号没建起来，不是读抖动（一个坏号连读 12 次全 599）；`start` 回 `success` + `taskid` 不证明任务真的在跑 |
| 曲库列表分页懒加载 | 一页 1000 首约 1.1 秒，整库 12331 首要 14.7 秒 |
